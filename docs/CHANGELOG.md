# Gripix Changelog

## 2026-08-12

- `founder-live-text-resize-reliability`: **Founder Live Text Resize Reliability**: Replaced paint-critical per-pointermove text re-layout with a two-phase resize interaction. While a desktop corner gesture is active, the existing complete text object and its canvas-level selection overlay receive the same transient compositor scale, so free-form, authored-newline, long, and bounded/template text retain their starting line structure and the handles track the rendered geometry without waiting for pointer release. At the gesture boundary, Gripix commits the final `fontSize` once and lets the established shared canvas-boundary contract deliberately reconcile the final wrapping; normal proportional resize still does not mutate `textBoxWidth`. Mobile text selection now relies on the contextual toolbar and selected state without the heavy desktop blue rectangle, while image/element and desktop selection chrome remain unchanged. Added Chrome/WebKit mid-gesture grow-and-shrink sampling for every representative text mode, including per-glyph containment, stable line count, wrapper/overlay scaling, handle alignment, and final font-size checks, plus iPhone/Android contextual-toolbar and selection/deselection coverage. Multi-Part Editable Element Colours remains deferred.

Free-form text still hugs short content and preserves authored Enter breaks, while long content now wraps at the real logical room around the item's centre; rotated text uses the matching horizontal/vertical projection. Explicit template/saved `textBoxWidth` remains authoritative, and corner resize still changes only `fontSize`. The live editor, hidden DOM export surface, and iPhone Safari canvas fallback consume the same calculated wrap width. Mobile Fit now runs the same fresh workspace measurement, scale, and zero-pan centre transaction as preset Fit instead of only resetting stored viewport values, avoiding stale ResizeObserver geometry after browser-chrome or responsive changes. Added desktop/mobile boundary, move, resize, newline, template, caret, export, fallback, and rendered Fit/centre coverage; expanded export fixtures to include boundary-wrapped and authored-newline text, a template, uploaded image, and element. Multi-Part Editable Element Colours remains deferred.

- `founder-qa-elements-repair`: **Elements Library Founder QA Repair Pass**: Fixed five issues found in manual Founder QA of the prior Elements Library Expansion sprint, without starting new feature work. (1) *Colour behaviour*: audited all 145 catalog elements for default colour, colour-mode correctness, and post-insertion visibility. 68 elements with a genuine dominant fill region (detected via two heuristics - relative-area and absolute-area, since a purely relative threshold missed founder-named examples like Sun and Ice Cream Cone whose small central shape is diluted by thin accessory strokes) were promoted from stroke-only to `colourMode: "fill-and-stroke"`, giving them a real Fill control instead of only Stroke. Moon was rebuilt from an evenodd two-circle construction (which rendered its authored blue fill with no way to change it) to a single-path crescent with `fill-and-stroke`, defaulting to black. Fish's eye dot was changed from a filled dot to an outlined one so it responds to the same colour controls as the rest of the glyph. (2) *Excessive stroke width destroying detailed artwork*: root cause was that `MAX_SHAPE_STROKE_WIDTH` (40) was applied uniformly regardless of how much internal negative space an element's geometry could tolerate before adjacent strokes merged into a filled blob (confirmed empirically by rasterizing each element's SVG and flood-filling to detect when internal holes collapse as stroke width increases). Fixed with a new optional per-element `maxStrokeWidth` field on `ElementAsset`, read through a shared `getEffectiveMaxStrokeWidth`/`effectiveMaxStrokeWidth` computation at all three stroke-width UI call sites (`EditorPreview.tsx`'s `changeShapeStrokeWidth`, `EditorInspector.tsx`, `MobileContextToolbar.tsx`), capping the UI's max at `min(MAX_SHAPE_STROKE_WIDTH, asset.maxStrokeWidth ?? MAX_SHAPE_STROKE_WIDTH)`. 35 elements with genuinely fragile multi-part detail (Pencil, Ice Cream Cone, Dotted Circle Border, etc.) were capped; simple single-outline shapes (Circle, Heart) were deliberately left at the full 40px range per the founder's explicit instruction not to weaken controls that legitimately support wide strokes. (3) *Re-selection of thin/open artwork*: `hitTesting.ts`'s `hitTestElement` was rewritten from native zero-tolerance `SVGGeometryElement.isPointInFill/isPointInStroke` to a Canvas2D `Path2D` + inflated-`lineWidth` `isPointInStroke` approach, adding the same screen-pixel click tolerance shapes already had (`SHAPE_HIT_TOLERANCE`: 2px desktop / 6px touch, converted into the SVG's own viewBox units at the item's current size and zoom) to graphic-kind elements, so thin/open glyphs like the Hashtag are reliably selectable a few pixels off their visible stroke without resorting to oversized rectangular hit areas. (4) *Recents and Favourites UX*: `ElementsPanel.tsx`'s Recents/Favourites row was rebuilt from a cramped 2-column grid (the source of the clipped headings/counts) to a full-width stacked layout, and a new `CollectionView` state lets either section's new "See all" button (given a disambiguating `aria-label` - "See all Recent" / "See all Favourites" - distinct from the unrelated per-category "See all (N)" buttons already in the default browsing view) open a full browsing view built from the same `ElementCard` grid used everywhere else, supporting insertion and favouriting, with a back button and empty states. Found and fixed a real bug in the process: `handleElementClick`'s "record as recent" `localStorage` write lived inside the `setRecentIds` updater function, but inserting an element auto-selects it, which on mobile unmounts the whole `ElementsPanel` in the same React batch - a fiber being torn down never gets its queued updater invoked, so the write silently never happened and Recents stayed permanently empty on mobile. Fixed by computing and writing the next recents list as a plain statement in the callback body, independent of whether the component's own re-render (and thus the updater) ever runs. (5) *Favourite control visibility*: `ElementCard`'s favourite star moved from an `opacity-0 group-hover:opacity-100` overlay on the thumbnail (invisible without hover, unusable on touch) to a permanent row beside the element name, with `aria-pressed` state, a real ~32px tap target, and strong contrast in both active/inactive states. Found and fixed a real keyboard-accessibility bug in the process: the card's own `onKeyDown` unconditionally called `preventDefault()` on Enter/Space, which suppressed the nested star button's native Enter-triggers-click behaviour and inserted the element instead of toggling the favourite whenever the star was keyboard-focused - fixed by ignoring keydown events that don't originate from the card itself (`event.target !== event.currentTarget`). **Multi-part editable elements** (e.g. independently recolourable bars in a chart) was scoped as a documented future feature only - the current single-fill/single-stroke-per-element architecture doesn't support it trivially, so a recommended data model (per-region `data-region` attributes, a `regionColours` field, a second `getElementSvgMarkup` code path, per-region inspector UI) was written up in `docs/POLISH_BACKLOG.md` §4 and pointed to from `docs/ROADMAP.md`, with no implementation attempted.

## 2026-08-05

- `founder-qa-dynamic-element-bounds`: **Dynamic Element Bounds Completion**: Fixed three regressions Founder QA found in the previous sprint's static selection-bounds fix. (1) *Dynamic bounds*: the prior fix baked each catalog asset's visible bounds into a static `visibleBounds` field computed once at a fixed reference stroke width, so increasing border/stroke width visually grew the artwork's stroke without the selection ring, resize handles, or drag area growing to match. Root cause fixed properly rather than patched: `ElementAsset.geometryBounds` now stores only the asset's pure, stroke-EXCLUDED path geometry (invariant to stroke width by definition - `getBBox()` never includes stroke), and a new shared function `getElementVisibleBounds(geometryBounds, strokeWidth, hasStroke)` inflates it by the item's *current* stroke half-width at render time inside `getElementSvgMarkup`, reading the actual final stroke state back off the substituted markup so it can never drift from what is actually painted. Because item.size (the wrapper) must stay a fixed zoom multiple of the true bounds for the selection ring/handles/drag/rotation pivot to keep matching, `changeShapeStroke`/`changeShapeStrokeWidth` in `EditorPreview.tsx` now rescale `item.size` by that same multiple whenever stroke width or stroke presence changes. `MAX_SHAPE_STROKE_WIDTH` raised from 20 to 40 so the full requested validation range is reachable. (2) *Line minimum size*: `getBoundedImageSize`'s minimum-size clamp constrains the *shorter* dimension, which is correct for photos but forced a naturally-thin Line's width to balloon (~368 units) just so its ~8-unit-tall stroke could clear an 8-unit floor. Added a dedicated `getBoundedElementSize` (constrains the *longer* dimension instead, floor 20 units) used for all Shape/Element sizing (insertion, pinch-resize, corner-drag resize); `getBoundedImageSize` itself is untouched and still used only for Images. (3) *Shared geometry*: the previous sprint's static bounds used two different stroke references depending on catalog `insertion.kind` (a `DEFAULT_SHAPE_STROKE_WIDTH` special case for 7 entries, each asset's own authored stroke width for the other 17); the new dynamic system has exactly one formula applied uniformly to all 24 catalog entries, with no per-kind branching. Verified with a new Playwright suite: border width swept 1px -> 40px with the selection box confirmed to grow and the rendered SVG confirmed to still exactly fill the wrapper, across **every one of the 24 catalog elements**; Line confirmed to insert near its intended footprint (not the old inflated size) and to shrink substantially via corner-drag without ballooning back out; and for the 10 explicitly named elements (Rectangle, Rounded Rectangle, Circle, Triangle, Diamond, Heart, Arrow, Line, Checkmark, Star) resize-to-minimum, resize-to-maximum, rotation-pivot stability, and undo/redo all confirmed correct. 240 passed, 0 failed (8 intentionally skipped - documented WebKit touch-constructor limitation from an earlier sprint) across Desktop Chrome, Desktop Safari, iPhone Safari, and Android Chrome, plus a second confirmation pass against the production build.

## 2026-08-04

- `founder-qa-accurate-selection-bounds`: **Accurate Selection Bounds for SVG Elements**: Selection rings, drag hit areas, and resize handles for catalog Elements (Line, Arrow, Heart, Rectangle, etc.) were sized to each asset's full authoring viewBox (a fixed "0 0 100 100" canvas every asset is drawn on) rather than the actual painted artwork, so thin/off-centre assets like the horizontal Line carried up to ~90% invisible padding in their interactive bounding box. Root cause: `ElementSvg.tsx` rendered every asset's raw, unmodified viewBox, so `item.size` (which drives the wrapper div that the selection ring, `CornerResizeHandles`, and drag hit-testing are all positioned against) represented the authoring canvas, not the artwork. Root-cause audit also covered Images and Text: both were already correct by construction (image resize is always aspect-locked so `object-contain` never letterboxes; text has no `size` field at all, sizing natively via CSS `max-content`) - neither was modified. Fix, scoped entirely to `components/editor/elements/`: measured each of the 24 catalog assets' true stroke-inclusive bounding box in a real browser (`getBBox` + explicit stroke-width expansion, matching the actual stroke-width each asset renders with post-insertion, including the `DEFAULT_SHAPE_STROKE_WIDTH` override applied to the 7 "shape-kind" entries), stored the result as a new `visibleBounds` field per `ElementAsset`, and crop `getElementSvgMarkup`'s render-time `viewBox` (canvas placement only - catalog thumbnails are unaffected, they render `element.svg` directly) to that tight box with `preserveAspectRatio="none"`, matching the existing Shape rendering convention. `defaultSize` was recalculated per asset to the corrected aspect ratio. Because the wrapper is the single source of truth for the selection ring, resize handles, drag hit area, and rotation pivot, none of that shared gesture code needed to change - it automatically became correct. Verified with a Playwright suite measuring the rendered wrapper against the artwork's true painted extent (sub-1.5px precision) across Line/Arrow/Heart/Circle/Rectangle, resize-handle positions, rotation-pivot stability, drag, undo/redo, and resize-after-fix, run across Desktop Chrome, Desktop Safari, iPhone Safari, and Android Chrome (100 passed, 0 failed, serial run with no parallel resource contention).
- `founder-qa-elements-resize`: **Elements Pinch-Resize Root-Cause Fix**: Traced why Elements pinch-resized in visible stepped increments on mobile Chrome and mobile Safari while Images and Text stayed smooth. Root cause (confirmed against the `react-dom` source): `ElementSvg.tsx` passed a brand-new `{ __html }` object to `dangerouslySetInnerHTML` on every render; React diffs that prop by object identity, not string content, so every pinch-resize frame (item.size changing, not fill/stroke) forced a full `domElement.innerHTML =` re-parse of the SVG subtree even though the markup never changed. Images (`<img>`, CSS-only resize) and Text (plain style writes) never paid this cost. Fix: memoized the `{ __html }` object in `ElementSvg.tsx` on `[asset, item.fill, item.stroke, item.strokeWidth]`, excluding size/position/rotation, so resize/drag/rotate no longer touch the SVG subtree at all. Verified with a Playwright `MutationObserver` regression test that fails on the pre-fix code (24 subtree replacements per gesture) and passes after the fix (0), across Chromium (Desktop Chrome, Android Chrome mobile emulation) and, via an equivalent pointer-drag test on the same render path, WebKit (Desktop Safari, iPhone Safari). Images and Text were not modified.
- `founder-qa-colourpicker-restore`: **Gripix Colour Picker Restoration**: Restored `ColorPicker.tsx` to the last verified-good, hand-built version (portal-rendered into `document.body`, draggable header, Escape-to-close, EyeDropper, HEX/RGB, hue/saturation/value square, opacity slider, preset swatches), after an intermediate "recovery sprint" commit had reimplemented it with subtly different behaviour (e.g. `click` vs `pointerdown` outside-close listener, always-rendered disabled EyeDropper button). No API changes; drop-in replacement for all existing call sites in `EditorInspector.tsx` / `TextToolbar.tsx` / `MobileContextToolbar.tsx`.
- Verified with `npm run lint` (0 errors, 4 pre-existing `<img>` warnings unchanged), `npx tsc --noEmit` (0 errors), `npm run build` (clean production build), and a real, visible Playwright pass across Desktop Chrome, Desktop Safari, iPhone Safari, and Android Chrome.
